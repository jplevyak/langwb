# langwb review — 2026-11-22

Reviewed at commit `7e3fe22` ("Add ROADMAP.md"), on macOS (Darwin), after
the four "Review Step N" commits that answered the
[2026-11-21 review](2026-11-21-review.md). `src/` has grown from ~3.7k to
~5.8k lines (+3.2k / −0.6k across 22 files). There are no changes to `ifa/`
or `dparser/`. `make test` passes: 31 smoke cases, all
`examples/minilang/*.ml`, and 33 cases in `tests/run_tests.sh`, in about 2 s.
Every finding below was reproduced with `./langwb -e` using the expression
quoted with it. §5 lists them all.

The top three:

1. **Make closures capture outer variables (§2.1).** `let a = 5 in let f =
   fn(x) => x + a in f(1)` fails inside IFA. The README advertises closures,
   and the guest macros in the tests already work around this by passing
   their environment as explicit parameters. Fix this before Step 5.
2. **Fix the correctness bugs in Step 4's contour cloning (§2.2).** Clone
   names are plain text and can be captured by user bindings. Case A deletes
   the original binding, so a function also used as a value becomes unbound.
   Then make the "demand" real by re-analysing the clones, which also gives
   the bounded fixpoint that Step 7 plans.
3. **Find top-level form boundaries with the grammar, not by scanning for
   `;` (§2.3).** Without this, user grammars that use `;` break as soon as
   another statement precedes them. Step 5.1 builds on this.

## 2. What needs attention

### 2.1 Closures do not capture outer variables

```
$ ./langwb -e "let a = 5 in let f = fn(x) => x + a in f(1)"
error: 'a' has no type
error: expression has no type
error: 'a' is used before assignment on every path; type is:
$ ./langwb -e "let mk = fn(a) => fn(x) => x + a in mk(5)(1)"
error: 'a' has no type ...
```

The resolution pass accepts these programs, so the failure comes from
lowering to IF1. The error reaches the user as an internal IFA diagnostic
with no location. ROADMAP Step 6 lists this as "ergonomics", but it is more
basic than that:

- The README describes minilang as having "lambdas/closures".
- Any `.lang` that desugars to `fn` and a free variable (a loop, a callback,
  `map`) fails at analysis time, far from the macro that produced the code.
- The tests already work around it.
  `rec loop = fn(c, n, i) => …` passes `c` and `n` explicitly because `loop`
  cannot close over them.

IFA already analyses closures. Its C and LLVM backends handle closure
creation sets, so this is a frontend lowering gap, not an analysis one.
Lower free variables either as IF1 closure slots or, more simply at first, by
lambda lifting: add each captured variable as an extra parameter at every
call site the resolution map can see.

### 2.2 Step 4's contour cloning

`Workbench::expand_stage1_contour_aware` (`src/workbench/workbench.cc:1351`)
is the most novel code in the repository and works on its showcase,
`examples/minilang/contour_spec.ml`. It has three correctness bugs and one
gap between what it does and what the ROADMAP describes.

**(a) Clone names are not hygienic.** Clones are bound as the text
`"__c_" + orig_name + "_" + g` (`:1409`, `:1501`), and the rewritten calls
keep the original callee's scope set (`rewrite_redirected_calls`, `:1298`).
A user binding with that name in a nested scope captures the call:

```
$ ./langwb -e "let f = fn(n) => pow_opt(2, n) in let __c_f_0 = fn(n) => 1000 in f(3) + f(4)"
1016          # expected 24
```

This is the same class of bug as the `__pat_x__` and `__a__` splice holes
(§2.6). Give each clone binder and its redirected references a fresh scope
from the `ScopeAllocator` that is already in hand. The text then no longer
matters.

**(b) Case A deletes the original binding.** When IFA has already split `f`
and the groups differ, the output binds only `__c_f_0 … __c_f_k`
(`:1422–1424`). Case B keeps the default `f`, but Case A does not. Any
reference to `f` that is not a direct call site becomes unbound:

```
$ ./langwb -e "let f = fn(p) => sum_fields(p) in let h = f in f({x:1,y:2}) + h({a:3,b:4})"
langwb: 1:42: unbound identifier 'f'
```

The error names the user's own, correctly bound `f`. Always keep the default
binding, as Case B does, and route non-call uses to it. Unreferenced
bindings are removed later anyway.

**(c) The "demand" is an override on the formal, not a split.** Case B
re-expands the lambda with an attribute override that sets the formal's node
to the call site's constant (`:1459–1482`). Nothing is re-analysed, so the
override reaches only an expression that *is* the formal. Anything derived
from it keeps the joined attributes:

```
$ ./langwb --dump-expanded -e "let f = fn(n) => pow_opt(2, n + 1) in f(3) + f(4)" | grep -c __c_f
0             # no clones; both calls take the generic path
```

The same limit applies one call deeper:
`let g = fn(n) => pow_opt(2, n) in let f = fn(n) => g(n) in f(3) + f(4)` is
not specialized either. The ROADMAP calls this "bounded demand-driven
constant splitting". It is that only for macro arguments that are literally a
formal of the enclosing `let`-bound lambda.

There is a cheap way to make it real without the IFA hook that ROADMAP
Step 7 holds in reserve. After Case B creates clones, **re-run IFA on the
rewritten program**. Each clone is now reachable only from call sites with a
constant argument, so IFA propagates the constant through `n + 1`, into
`g`, and so on. A second Stage-1 pass then sees real facts. That is the
"bounded `analyze → Stage-1 → analyze` iteration" from Step 7. With
`kMaxValueSplits` as the bound, and the fallback as the end state, it
terminates. Do this before adding more cases to the syntactic matcher.

**(d) Smaller issues:**

- `syntax_sig` (`:1254`) ignores scope sets. Two expansions whose text
  matches but whose identifiers bind differently would be merged into one
  clone. Include a canonical form of the scopes, or the resolved binder ids.
- Guest Stage-1 macros now run once per contour, plus once for the default
  and once per demanded call site. A macro with effects (`grammar_add_rule`,
  `stx_set_prop` on shared nodes) repeats them. Either document that Stage-1
  macros must be pure, or discard effects from expansions that are not kept.
- Only `let f = fn(...)` is recognised (`unwrap_lambda_stx`). `{ def f = …;
  f(3) + f(4) }` and `rec f = …` are not cloned. The ROADMAP lists `def` for
  Step 7. It shares the binding-site logic with (b), so do them together.

### 2.3 Top-level forms are still found by scanning for `;`

Declaration *heads* are now parsed with `decl_grammar_.parse_prefix`, which
is good. But `eval_i64` (`workbench.cc:1153`, `:1184`) still decides where an
ordinary form ends with the hand-written `find_decl_terminator`. It still
detects declarations with `match_keyword` (`:254`). A grammar whose
expressions contain `;` therefore works only on a narrow path, when the
*entire* remainder parses as one expression and nothing precedes it:

```
$ ./langwb -e '<grammar for "x := e; body">  x := 10; y := x * 4; y + 2'
42
$ ./langwb -e '<same grammar>  def a = 2; x := 10; x * a'
langwb: 1:7: syntax error
```

The previous review's §4.1 asked for this: parse the next form at `stmt`
with the current grammar, taking the longest prefix (`parse_prefix` already
exists for declarations), then expect `;` or end of input. The same change
removes three more textual pieces:

- Declaration keywords (`macro`, `prim`, `hook`, …) are reserved everywhere,
  whatever the `#lang`, because `starts_with_decl` runs before any grammar
  does.
- Macro bodies are `body_text`, balanced opaque text that is re-parsed
  later, and `core(...)` is the regex `"[^)]+"` (`:183`) parsed by hand. Use
  `expr` and a real `core_body` rule. Errors in a body then point at the
  declaration, not at a later re-parse.
- The declaration grammar cannot be extended from a `.lang` file. Allowing
  `grammar decl += …` would let a language add its own declaration forms,
  which is the last step of the previous review's §2.5.

ROADMAP 5.1 Phase 1 needs this too: an opaque balanced span ends where the
grammar says, not at the next `;`.

### 2.4 `stx_binding_eq` is `bound-identifier=?`, not `free-identifier=?`

`_CG_stx_binding_eq` (`src/ifa_bridge/meta_abi.cc:181`) returns true when
the text *and* the scope sets are equal. That is Racket's
`bound-identifier=?`, which answers "would one binder capture the other?".
The use case the last review gave, recognising a literal such as `else` or
`otherwise` hygienically, needs `free-identifier=?`, which asks "do they
refer to the same binding, or are both unbound with the same name?":

```
$ ./langwb -e 'macro is_else => let c = stx_call() in
    if stx_binding_eq(stx_arg(c, 0), stx_parse("expr", "otherwise")) != 0
    then stx_parse("expr", "1") else stx_parse("expr", "0");
  is_else(otherwise) * 10 + is_else(foo)'
0             # free-identifier=? gives 10
```

The template's `otherwise` carries the macro's intro scope, so the scope sets
never match. Both predicates are useful. Rename this one
`stx_bound_id_eq`, and add `stx_free_id_eq` on top of the resolution map from
Step 2, which already has the information.

### 2.5 IFA errors are still unlocated, and now matter more

```
$ ./langwb -e "let p = {a: 1} in p.b"
error: unresolved member 'b' of class '__wb_rec_1'
$ ./langwb -e "let f = fn(x) => x in f(1) + f({a:1})"
error: illegal primitive argument type expression illegal: __wb_rec_2
```

These are unchanged since the last review. They now cost more, because every
bug in §2.1–§2.2 also surfaces as an internal IFA message with no location.
The provenance needed is already on `SyntaxObj` (`line`, `col`,
`origin_macro`). Carrying it onto the IF1 symbols when they are created, and
mapping record classes back to their literal's span, is small work. Pull this
forward from Step 7. It is what makes the other gaps debuggable for anyone
writing a `.lang`.

### 2.6 Identifiers are still generated as text

There are now three places that make identifiers by spelling them:

- `stx_splice` holes (`__a__`)
- `syntax_rule` slots (`__pat_x__`, `__pat_xs_k__`; `workbench.cc:905–954`)
- contour clone names (§2.2a)

Each one can collide with a user identifier. A single internal facility,
*fresh identifier = name + fresh scope*, would fix all three, and the
grammar-checked quasiquote planned in Step 6 would remove the first two from
the surface language. Since this is one root cause, schedule it once,
early.

### 2.7 Code structure and tests

- **`workbench.cc` is 1.6k lines doing five jobs:** declaration parsing,
  `syntax_rule` compilation, `#lang` loading, contour cloning, and two
  evaluation drivers. `eval_i64`'s module path and `eval_single_expr_i64`
  each run the analyse → Stage-1 → dump → JIT sequence. `bridge.cc` grew by
  ~1k lines. Move contour cloning into its own file
  (`workbench/contour_clone.cc`) and give the staged pipeline one entry point
  before Step 5 adds `amb` resolution to it.
- **There are two test suites.** The 31 smoke cases are still hard-coded in
  `src/cli/main.cc`, next to `tests/run_tests.sh`. Moving them into the
  script, or a `tests/*.ml` + `.expected` layout, would make one place to add
  regressions.
- **The "golden" checks are substring checks.**
  `golden_dump_expanded_unroll` checks only that the header
  `=== Expanded SyntaxObj ===` is printed, so it passes whatever the
  expansion is. Use whole-file goldens with the scope ids normalised.
- **Add every repro in §5 as a test,** marked expected-fail until fixed. Each
  is one line in the existing runner.

### 2.8 Process

Each "Review Step N" commit is large (Step 4 alone rewrote ~1k lines of
`bridge.cc` and `workbench.cc`), and all four landed on the same day. The
commit messages are accurate, but bugs such as §2.2(a) and (b) are the kind
that one focused, smaller commit per mechanism, each with its own adversarial
tests, tends to catch. The README's limitations section should also mention
closures (§2.1) and the `;`-splitting rule (§2.3).

## 3. The roadmap

The ROADMAP's direction is right: scoped syntax and ambiguity as data
(Step 5) are the research questions that make this tool distinctive. The
order is the issue. Steps 5–8 assume a core that §2.1–§2.4 show is not yet
solid, and some items in later steps are prerequisites for earlier ones.

**Insert a short hardening step before Step 5:**

1. Closure capture (§2.1), moved from Step 6.
2. Contour-clone fixes: hygienic names, keep the default binding, include
   scopes in `syntax_sig` (§2.2a, b, d).
3. Grammar-driven top-level form boundaries and declaration bodies (§2.3).
4. `stx_free_id_eq` (§2.4).
5. Source-mapped IFA diagnostics (§2.5), moved from Step 7.
6. One fresh-identifier facility (§2.6).

Each item is small, and each removes a way for a `.lang` author to get an
internal error far from its cause.

**Step 5.** Do 5.3 (grammar hygiene) first. It is small and reuses the
fresh-identifier facility. Then 5.1, then 5.2. For 5.2, one constraint should
be added: DParser's `ambiguity_fn` runs during the parse and must return one
node, so the `amb` node has to be built by recording the alternatives on the
side and keying them by the returned node. This is the "shared plumbing"
point from the last review's §4.5. Plan the per-rule action-index table that
5.1 Phase 2 needs at the same time, since `CoreRuleMeta` is already indexed
that way.

**Step 6.** Closures move out of this step. Do grammar-checked quasiquote
next, because it removes the textual templates (§2.6). Then lists and
`match`. Then non-`int64` results.

**Step 7.** The bounded `analyze → Stage-1 → analyze` iteration is the real
implementation of §2.2(c), so move it next to the Step 4 fixes, not after
Step 6. With that loop, the upstream IFA demand hook may never be needed.
Keep it optional, as the ROADMAP already does.

**Step 8.** No change. An LSP needs §2.5's source maps first, which the
reordering above provides.

## 4. Summary

The previous review asked for core role annotations, a resolution pass,
`letrec`, partial expansion, Stage-1 fallbacks, per-contour attributes and a
self-hosted prelude. All of these now exist, and the `--bare` +
`prelude.lang` result is a real milestone. What remains is mostly
consolidation: Step 4's cloning has three correctness bugs and models a
demand it does not yet make; closures do not capture; and the top level is
still split by text. Fixing these before Step 5 is cheaper than fixing them
under scoped syntax and `amb` nodes.

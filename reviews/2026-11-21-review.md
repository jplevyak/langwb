# langwb review — 2026-11-21

Reviewed at commit `aad1dad` ("Complete Zero-C++ Step 4"), on Linux, LLVM 20
toolchain. The workbench's own code is ~3.7k lines in `src/` over the vendored
`ifa/` (~160k) and `dparser/` (~66k) subtrees. Everything below was checked by
building from a fresh clone, running `make test`, and probing `./langwb -e`
with the expressions quoted in each finding.

The top three:

1. Fix the fresh-clone build (§2.1).
2. Make Stage-1 contour-aware: expose per-contour facts, and let a Stage-1
   query act as a demand that makes IFA split (§2.2). This is the capability
   nothing else has.
3. Make binding forms declarable, and parse declarations with the workbench's
   own grammar, so "zero C++" is true (§2.4, §2.5). Runtime grammar extension
   (§4) builds on the second half of this.

---

## 1. What it does well

- **The pipeline is the right shape.** Parse → hygienic Stage-0 expansion →
  IFA → Stage-1 attribute-driven expansion → IFA → LLJIT. Letting macros see
  *whole-program inferred* facts is something Racket and Rust macros cannot
  do, and it is the reason this project is worth building.
- **Grammars are compiled in memory and composable.** `GrammarDef` →
  `mkdparse_from_string` → binary tables in a buffer, with a content-addressed
  `GrammarCache` and parsing from any non-terminal (`start_state`). No disk,
  no `dlopen`. `grammar expr += ...` inside a `.lang` file is a real feature.
- **The hygiene is a faithful sets-of-scopes model.** Flip the intro scope on
  input and output, fresh scopes on binders, Flatt's maximal-subset
  resolution in `BindingEnv`, and an explicit escape (`unhygienic_ident`) for
  anaphoric macros. `with_tmp` and `triple` do not capture; `aif` binds `it`.
- **Transfer functions in the guest language.**
  `prim my_abs c_call "labs" transfer => ...` folds constants inside IFA's
  lattice and still calls libc at run time. That is a good demonstration of
  the "frontend-injected semantics" idea.
- **Subtree changes are small and upstreamable.** About 90 lines in
  `ifa/codegen` (JIT/LLVM hooks) and none in `dparser/`.
- **It is fast enough to iterate on.** ~30 ms for `-e "1+1"`, ~50 ms for
  `examples/minilang/dsl.ml` (two grammar extensions, four guest macros
  JIT-compiled), end to end.

## 2. What it does less well

### 2.1 A fresh clone does not build

```
clang    -c -o dparser/version.o dparser/version.c
dparser/version.c:9:36: error: use of undeclared identifier 'D_MAJOR_VERSION'
```

`Makefile:89` declares `dparser/version.o` as depending on
`dparser/libdparse_gc.a` with no recipe. The sub-make builds `version.o`
*before* it archives `libdparse_gc.a`, so `version.o` is older than its
prerequisite, and the top-level make rebuilds it with the built-in
`%.o: %.c` rule, without dparser's `-DD_MAJOR_VERSION`. This is deterministic,
not a `-j` race. Fix: an empty recipe (`... : $(DPARSER_DIR)/libdparse_gc.a ;`)
or a grouped target (`&:`) on the sub-make rule.

### 2.2 Stage-1 cannot see, or ask for, per-contour facts

Two separate problems, which a single example makes look like one:

```
$ ./langwb -e "let f = fn(n) => pow_opt(2, n) in f(3)"
8
$ ./langwb -e "let f = fn(n) => pow_opt(2, n) in f(3) + f(4)"
langwb: evaluation failed
```

With the contour count added to `--dump-attrs` (a local debug print, not
committed):

```
let f = fn(n) => pow_opt(2, n) in f(3) + f(4)
    expr "n" [type=int64 ctr=1]             <- ONE contour; n in {3,4}

let f = fn(n) => n in f(3) + f({a: 1}).a
    expr "n" [type=__wb_rec_2|int64 ctr=2]  <- two contours, then joined
```

**(a) Contours are joined.** `extract_sym_attr`
(`src/ifa_bridge/bridge.cc:336`) iterates every `EntrySet` of the owning
function and merges them into one `NodeAttr` per syntax node. Where IFA did
split, as in the second example, Stage-1 sees `record|int64` and cannot tell
the contours apart.

**(b) The contour a macro needs may not exist.** In the first example both
calls pass `int64`, so IFA (correctly, by its own split-on-demand rule) made
one contour for `f`, and `n` is non-constant inside it. No reading of the
attributes, joined or not, can make `pow_opt` succeed. The macro's question
has to be able to *cause* the split.

There is also a structural issue. Stage-1 rewrites **syntax**, and one syntax
node is shared by every contour, so even exact per-contour facts have nowhere
to go. The options, with their trade-offs:

**A. Attributes per (node, contour); Stage-1 clones function bodies in
syntax.**
Keeps macros syntax→syntax: hygiene, grammar templates, source locations and
`--dump-expanded` all keep working, and the first step is cheap (stop merging
in `extract_sym_attr`, add a contour index to the Meta-ABI). Two costs:

- *Contours have no syntactic address.* An EntrySet is reached through call
  edges, not a piece of source. Giving clone *k* its own rewrite means
  redirecting exactly the calls that land in *k*. If the caller is itself
  shared across contours, the caller must be cloned too, up the chain, and
  with first-class functions (stored in a record, then called) the call site
  may not determine the contour at all. In general this is ifa's `clone.cc`
  reimplemented over syntax.
- *Contour identity does not survive `ifa_reset()`*: EntrySet numbering is
  per run.

Both shrink if clones are keyed by the macro's **decision**, not by contour:
run the macro once per contour, group contours by the syntax it returns, and
clone only when the groups differ. That is demand-driven (no clone unless a
macro observed a difference), stable across resets, and keys on what a value
*is* rather than where it came from. Typical programs then need few clones,
and most of the redirect problem goes away.

**B. Run Stage-1 after IFA's cloning.**

- *B1, rewrite IF1.* Facts are exact per clone and ifa has already
  redirected every call, first-class ones included. But macros become IR
  transforms: no grammar templates or source-level errors, and the guest ABI
  must grow an IF1 construction API. That is a different product from a
  syntax workbench. ifa's pipeline (clone → optimize → codegen) is also not
  built to re-enter analysis after a rewrite, which any type-changing rewrite
  needs.
- *B2, emit one syntax copy per IFA clone, then expand and re-analyse.*
  Macros stay syntactic and ifa chooses the redirects, but every clone becomes
  source whether or not a macro cares (bloat), and one pass's cloning
  decisions get frozen into the program, against ifa's model of re-deriving
  decisions at convergence.

Both B variants share a flaw: IFA clones on **types**, so B can only rewrite
distinctions the analysis already made. It does nothing for (b).

**C. The Stage-1 query is a demand on IFA.**
`pow_opt` asking "is `n` constant?" and getting "no, two constants merged" is
exactly a demand in ifa's sense: something observing a distinction and unable
to proceed. Report it through an `IFACallbacks` hook; IFA splits `f`'s
contour on that formal's constant value (constants are already singleton
CreationSets, so the lattice can express it) and re-runs. A or B then
delivers the per-contour rewrite. This is the only option that fixes (b), it
keeps splitting demand-driven and scoped to formals a macro actually asked
about, and it makes Stage-1 a participant in inference rather than a reader
of it. Costs:

- *Termination.* `r(n - 1)` yields unboundedly many constants. The demand
  needs a bound, such as "split only on values that change the macro's
  decision" or a per-formal cap after which the macro's fallback runs. This
  is why §2.3 matters.
- *An analyse → expand → analyse loop*, with its convergence questions (§3).
- *An ifa change*: a callback through which a frontend nominates a split,
  reviewed against ifa's split-only-on-demand rules.

| | fixes (b) `f(3)+f(4)` | fixes (a) joins | macro API | cost |
|---|---|---|---|---|
| A, keyed by decision | no | yes | syntax | medium |
| B1, IF1 | no | yes | IR | high |
| B2, per-clone syntax | no | yes | syntax | medium, bloats |
| C + A | **yes** | yes | syntax | high |

**Recommendation: C on top of A keyed by decision**, in this order:

1. Expose per-contour attributes and the contour count to guest macros
   (`contour_count` is already in `NodeAttr`). Cheap; fixes (a).
2. Stage-1 fallbacks (§2.3), which C needs in order to stop splitting.
3. A, keyed by decision.
4. The demand hook in ifa.

B1 solves a different problem (IR-level macros) and is worth doing only as a
separate feature. The target demo is *the same function body specialised
differently per value or type its callers supply, by a user-written macro
whose question caused the split*.

### 2.3 Stage-1 macros have no fallback

`pow_opt`, `if_const` and `sum_fields` are registered as placeholder
primitives (`workbench.cc:519`). When the macro's test fails (the exponent is
not a constant), the placeholder is left in the program, and compilation
fails with no message (above). A Stage-1 macro should be able to return
"no rewrite", leaving a generic runtime definition in place, and a failure
should say which macro declined and why.

### 2.4 The expander has minilang built in

`MacroExpander::expand_node` (`src/macro/expander.cc`) recognises:

- `let`: a 6-child node whose children read `let`, `=`, `in`;
- `fn`: a 6-child node whose children read `fn`, `(`, `)`, `=>`;
- a call: a 4-child node with `(` and `)`;
- a datum (for `hook datum`): a token whose first character is a digit.

A `.lang` with different binding syntax (`where` clauses, pattern binders,
`for x in ...`) gets no hygiene without C++. For the zero-C++ claim to hold,
binding structure must be declarable. A modifier on grammar rules would do
it, in the spirit of Spoofax's name-binding language, for example:

```
grammar expr += "'let' ident '=' expr 'in' expr" binds(1) scope(5);
grammar expr += "'fn' '(' params ')' '=>' expr"  binds(2) scope(5);
grammar expr += "ident '(' args ')'"             app(0, 2);
grammar expr += "\"[0-9]+\""                     datum;
```

The expander then reads the roles from the rule instead of the text.

### 2.5 The language for defining languages is not built with the workbench

`Workbench::apply_decl` parses `grammar`, `macro`, `form_macro`,
`stage1_macro`, `prim` and `hook` with hand-written `match_keyword` scanning.
Declarations are found by scanning for `;` (`find_decl_terminator`), and they
must all precede the program text. The declaration language should be a
`GrammarDef` the workbench owns and users can extend. That is also the
precondition for §4.

### 2.6 Templates are spliced by identifier text

```
let t = stx_parse("expr", "if __c__ then __a__ else __b__") in
let t1 = stx_splice(t, "__c__", stx_child(f, 1)) in ...
```

`apply_splices` replaces any identifier whose text matches a key, so a user
identifier named `__c__` collides. There is no repetition (ellipsis), and each
hole costs a `let`. A real quasiquote, with holes checked against the
grammar, would make `.lang` files several times shorter:

```
form_macro when_expr => `[expr| if ,(child 1) then ,(child 3) else ,(child 5) ];
```

Because DParser can start at any non-terminal, the hole's non-terminal can be
checked when the template is parsed, not when it fails downstream.

### 2.7 The guest language is too small to write real macros in

- `let` is not recursive, and there is no `letrec`, loop, mutation, list or
  `match` (SKETCH §7.5 lists `match`).
- Results are `int64` only (`eval_i64`). Meta-level values are int64 handles.
- Recursion produces an internal error, not a scoping error:

  ```
  $ ./langwb -e "let r = fn(n) => if n < 1 then 0 else n + r(n - 1) in r(10)"
  fail: undefined primitive transfer function 'r'
  ```

  `let x = 1 in y + 1` correctly reports `unbound identifier 'y'`, so the
  unbound check misses callees: an unbound name in call position falls
  through to primitive lookup.

Until macros can recurse over trees and iterate over lists (fields of a
record, children of a node), anything beyond one-shot templates has to be
written in C++.

### 2.8 Errors do not point at source

```
$ ./langwb -e "let p = {a: 1} in p.b"
error: unresolved member 'b' of class '__wb_rec_1'
error: expression has no type
```

No line or column, and an internal record name, although `SyntaxObj` carries
`line`/`col`. With macros in the pipeline this matters more: an error in
expanded code needs a trace back through the expansions (macro name, call
site, template). Carrying the origin on `SyntaxObj` (a `srcloc` plus an
expansion-history chain) and mapping IFA's `Sym`/`PNode` back to `node_id`
would cover both.

### 2.9 Testing is thin

- `tests/` holds only `.gitkeep`. The 29 smoke cases are hard-coded in
  `src/cli/main.cc`.
- A passing `make test` prints `:1: syntax error after '+'` from a negative
  case, which reads as a failure.
- There are no golden tests of expansion (`--dump-expanded`) or attributes
  (`--dump-attrs`), and no negative tests for the error paths above.
- Hygiene is tested only shallowly. Worth adding: nested macro uses, a macro
  that defines a macro, a macro that introduces a binder another macro
  references, and the `aif` escape inside another macro.

A directory of `.ml` files with expected output (or expected diagnostics) and
a runner would cover most of this.

### 2.10 The README claims more than the code does

All 18 commits are from one day, each "Complete Phase N". The README says
"complete languages can be defined purely inside `.lang` modules with zero
C++", which §2.4–§2.7 contradict. A short *Status and limitations* section
(per-contour attributes, built-in binding forms, `int64`-only, no recursion,
prefix-only declarations) would set expectations correctly.

## 3. Other gaps and directions

- **Iterate expansion and analysis to a fixed point.** The pipeline is a
  fixed sequence: expand, analyse, expand, analyse. Letting Stage-1 output
  trigger re-analysis until nothing changes makes macros *participants* in
  inference. It raises real questions (termination, monotonicity of the
  rewrites, what persists across passes), and `PrimRegistry` already has a
  monotonicity checker for transfer functions to build on.
- **Declarative static semantics.** Beyond binding (§2.4), a `.lang` should be
  able to declare checks over IFA's results and report errors in its own
  terms, rather than surfacing IFA's.
- **Use GLR ambiguity on purpose.** DParser keeps every parse of an ambiguous
  input, and nothing uses that yet. Composing two independently written
  extensions and resolving their overlap by priority, by scope (§4), or by
  types from IFA is a natural research direction for this tool.
- **Editor and LSP service.** With in-memory grammars, source spans and
  per-node attributes, hover-to-see-inferred-type and show-expansion are cheap
  and valuable in a language lab.
- **An AOT path.** Everything runs through LLJIT. `langwb build x.ml -o x`
  using ifa's LLVM AOT backend would show the compiler side, not only the REPL
  side.
- **IFA's process-global state.** Every stage serialises on `ifa_reset()`.
  `comptime` inside a macro that itself runs during analysis will need the
  `IFAContext` refactor SKETCH §2.1 names; doing it before more code depends on
  the globals is cheaper.
- **Cite the neighbours.** Spoofax/SDF3 and its name-binding language (§2.4),
  Rust proc macros and Zig `comptime` (staging), MetaOCaml (typed staging),
  Racket's `#lang` and reader. SKETCH §8 already covers Racket; the others
  help a reader see what is new here.

## 4. Extending the grammar at run time

Today a grammar extension is **file-global, prefix-only, and compile-time
only**. `eval_i64` (`workbench.cc`) applies every leading declaration to a
per-file `Workbench` clone, then parses the whole remainder once with the
resulting grammar. There is also `grammar_add_rule` in the Meta-ABI
(`meta_abi.cc:121`), but by the time guest code runs, the parse it could have
affected is over.

Extending at run time makes sense, and DParser is unusually well suited to it:
tables compile in memory, `GrammarCache` makes recompiles of a seen grammar
free, and parsing can start at any non-terminal. Measured cost today: a full
`dsl.ml` run (two extensions, recompile, four guest-macro JITs, analysis,
execution) takes ~50 ms against ~30 ms for `1+1`, so a recompile per
declaration is affordable at these grammar sizes. That should be re-measured
on a grammar a few hundred rules big before committing to per-form
recompilation.

"Run time" covers four distinct things, in increasing order of ambition.

### 4.1 Mid-file extension: a declaration affects what follows it

Make a module a sequence of top-level forms, and parse **one form at a time**:

1. Parse the next form with the current grammar at a `toplevel` start symbol,
   taking the longest prefix (DParser supports partial parses).
2. If it is a declaration, apply it, recompile (or hit the cache), and
   continue from where the form ended.
3. Otherwise, expand it and append it to the module.

This is how Lisp readers and Racket module bodies behave, and it removes the
"declarations must come first" rule. It needs §2.5 (declarations parsed by a
grammar) and a `toplevel` non-terminal. It is the smallest change with the
largest user-visible payoff, and it is the first one to do.

### 4.2 Scoped extension: syntax active only in a region

```
using syntax sql in
  select x from t where x > 3
```

The base grammar parses `using syntax NAME in <region>` with the region held
as an opaque balanced span (a raw token tree, as Rust's macros do). The
expander then re-parses the span with the base grammar plus `NAME`, starting
at `expr`. Scopes compose by nesting, and two extensions that conflict only
collide where both are in scope, which is the case §3's "use GLR ambiguity
on purpose" wants to study. The opaque span needs only a lexical rule for
balanced delimiters, so DParser needs no changes.

### 4.3 Macro-generated grammar

Let Stage-0 guest code produce grammar rules (the existing
`grammar_add_rule`) **and** have them take effect for the forms that follow,
which §4.1 provides. A macro could then derive syntax from data: a record
declaration that also generates a literal syntax for that record, or an
`enum` that adds its variants as keywords. Two things to decide:

- **Hygiene for grammar names.** Two macros generating a production named
  `item` should not merge. Non-terminals introduced by a macro should get its
  intro scope, as identifiers do.
- **Determinism.** If grammar construction depends on Stage-1 attributes, the
  parse depends on analysis, which depends on the parse. Keep grammar
  generation at Stage-0 unless there is a design for iterating that loop.

### 4.4 Grammars as a library for compiled programs

Expose `GrammarDef` / `DynamicGrammar` as a runtime library, so a *program*
compiled by langwb can build a parser at its own run time: a DSL interpreter,
a config loader whose syntax is defined by plug-ins. This turns DParser's
in-memory compilation into a user-facing feature and is a good showcase.
It depends on §2.7 (strings, lists, recursion in the guest language) and on
AOT binaries linking the dparser runtime. It is the furthest out of the four.

**Recommendation:** do 4.1 together with §2.5 now, 4.2 next (it is what makes
composing languages safe), 4.3 when the guest language can express it, and
treat 4.4 as a later showcase.

## 5. Reproducing the findings

```sh
git clone https://github.com/jplevyak/langwb && cd langwb
make -j               # fails at dparser/version.o (§2.1)
make -C dparser version.o && make -j && make test

./langwb -e "let f = fn(n) => pow_opt(2, n) in f(3) + f(4)"     # §2.2(b), §2.3
./langwb --dump-attrs -e "let f = fn(n) => n in f(3) + f({a: 1}).a"  # §2.2(a)
./langwb -e "let r = fn(n) => if n < 1 then 0 else n + r(n - 1) in r(10)"  # §2.7
./langwb -e "let p = {a: 1} in p.b"                             # §2.8
./langwb -e "let f = fn(x) => x in f(1) + f({a:1})"             # §2.8
```
